### D. 규칙 엔진 과대계상 수정 (선택 · 발표 리스크)

`frontend/src/api/mock/engine.js` 의 `optimize()` 가 **월 3,377원(14%) 부풀려서** 계산한다.

- **원인**: 채널을 하나씩 독립 평가하는 그리디인데, **항목별 월한도는 카드 단위**다. 두 채널의 같은 카테고리 결제를 한 카드로 옮기면 한도가 두 번 적용된다.
- 문서상 산출로직 ⑤ 정의는 "조합 중 최대"인데 구현은 조합 탐색이 아니다.
- **해결**: 채널 4개 × 카드 2~3장 = 최대 81개 조합이라 **완전탐색 가능**. 각 배치안마다 카드별로 거래를 모아 한 번에 `effectiveBenefit()` 을 돌리면 한도가 정확히 적용된다.
- 발표에서 "한도는 어떻게 처리했나요?" 질문이 나오면 걸릴 수 있는 지점.

### E. 백엔드 (배점 0점 · 여유 있을 때만)

Spring Boot 3 + JPA + H2로 하기로 결정했으나 `backend/` 는 비어 있다.
`engine.js` 를 `BenefitCalculator.java` 로 그대로 포팅하면 되고, 프론트는 `frontend/src/api/client.js` 의 `MODE` 를 `'http'` 로 바꾸면 실서버에 붙는다.

## 3. 설계 결정 (발표에서 쓸 것)

### 엔티티를 11개 → 14개로 늘림

기획서(PLANNING.md)의 11개로는 **핵심 로직이 계산 불가능**해서 3개를 추가했다.

| 추가 | 이유 |
|---|---|
| `transactions` | 인정실적 = Σ(**결제액** × …) 인데 그 결제액을 담을 테이블이 없었다. 외부 액터 수신처도 없었음 |
| `card_performance_tiers` | 실적 구간(카드 단위)을 `benefit_rules`(카테고리 단위)에 섞으면 정규화가 깨짐 |
| `point_balances` | 화면 3의 포인트 잔액·소멸예정 대응 컬럼이 없었음 |

### 설계 핵심 2가지 (발표 4:00 구간)

1. **`card_channel_rates`** — 채널 인정률은 카드 속성도 채널 속성도 아닌 **(카드 × 채널) 교차 속성**. 이 분리가 화면 7 시뮬레이션과 화면 8 차등 정책의 구현 가능 여부를 결정했다.
2. **`recommendation_details.snapshot_*`** — 혜택 규칙은 변경되므로 규칙 FK로만 저장하면 과거 제안 근거가 소실된다. 계산 시점의 인정률·할인율·한도를 **값으로 복사**해 보관.

### 저장하지 않는 리소스

화면 6 대시보드 지표와 화면 7 시뮬레이션·세그먼트 결과는 **저장 테이블을 두지 않는다.** 거래에서 실시간 집계한다.
→ 그래서 UI에도 "이력" 메뉴가 없다. **UI에 없는 기능은 API에도 두지 않는다**는 원칙으로 3자 정합성을 유지했다.

## 5. 지켜야 할 규칙

- **배경 흰색 / Pretendard / 본문 16px.** 폰트는 두 번에 걸쳐 +2px 올린 결과이므로 줄이지 말 것.
- **개발자용 안내 문구를 화면에 노출하지 않는다.** `status = NO_CHANGE_NEEDED`, `422 INSUFFICIENT_...`, `field: ...`, 에러 토스트의 `(401)` 같은 것. 예외 동작 자체는 유지하되 코드·스펙 용어만 제거. 설계 근거 설명은 **PDF에만** 둔다.
- **타사 카드 비교는 절대 넣지 않는다.** 화면 5의 `자사 상품 참고`는 자사 카탈로그 한정이며, 점선으로 분리해 메인 제안(보유 카드 재배치)을 침범하지 않게 유지할 것.
- **시간 부족 시 잘라낼 순서**: 카드사 세그먼트 추출 → 포인트 잔액·만료 → 실적 구간 근접 알림.
  **절대 자르면 안 되는 것**: 와이어프레임 전체, API 에러 코드 정의.
